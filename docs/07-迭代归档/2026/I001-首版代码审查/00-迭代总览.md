## 首版建议与边界

以下是讨论形成的推荐方案，新任务结合源码自主解决常规实现选择，实质范围变化再询问。

- /review：暂存、未暂存、未跟踪改动；无改动不偷偷回看上一提交。
- /review --staged：读取 index 内容，不能用工作区内容冒充暂存版本。
- /review --base main：merge-base 到 HEAD 的分支已提交差异，报告明确是否包含未提交改动；推荐不包含。
- /review --commit <sha>：指定提交变更；merge commit 采用明确且展示出来的父提交策略。
- /review src：路径过滤。
- 独立审查 Agent、必要项目规则与环境、受控读取/搜索/Git 查询、超时取消、结构化报告。
- 报告本次新增且可验证的缺陷；明确场景、影响、路径、diff 位置、P0-P3 优先级。允许零发现，不将置信度当成实测准确率。
- 必须覆盖删除、纯删除、重命名，保留 diff 两侧位置；历史审查的内容与上下文必须对应目标版本。
- 默认只审查，不修复、不发 GitHub 评论。不开放可绕过只读边界的任意终端调用。测试执行与只读承诺需明确区分。
- 区分完成零发现、完成有发现、部分覆盖、失败、中断、输出无效、快照过期。
- 第一版无需复杂前端、多 Agent 审查或自动修复；先确保宿主实际可用。
